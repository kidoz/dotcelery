# DotCelery 1.0.0

The first release of **DotCelery**: a distributed task queue for .NET 10 that speaks Celery's
message shape, keeps every storage choice explicit, and generates the dispatch path instead of
reflecting over it.

Its headline is the production shape of the library. A task travels through RabbitMQ, Redis
Streams, Amazon SQS, or the in-memory broker with the same contract, and its result lands in
Redis, PostgreSQL, SQL Server, MongoDB, or memory. Under both sits one storage model — documents,
leases, queues, counters, and notifications — implemented once for every store and held to the
same conformance suite on five providers. Around it are the pieces a long-running deployment
needs: canvas workflows, batches, sagas, a leader-elected Beat scheduler, message signing, an
inbox that refuses replays, a dashboard on real worker and task data, and OpenTelemetry metrics
and traces.

**Brokers and backends.** RabbitMQ publishes with confirms and mandatory routing and accepts
configurable queue arguments; Redis reads through consumer groups; SQS renews visibility while a
task runs and holds a message until its ETA within the 15-minute ceiling, leaving longer delays
to the worker; the in-memory broker models the others' delivery and settlement so tests exercise
realistic behavior. A broker declares what it guarantees beyond the delivery contract through
`IBrokerCapabilities`, and every broker runs the same contract suite.

**One storage model, five providers.** Results, leases, delayed messages, queue metrics,
historical metrics, batches, sagas, dead letters, outbox, inbox, signals, revocations, partition
locks, execution tracking, and rate limiting are built once in `DotCelery.Core.Storage.Stores` on
the storage primitives. PostgreSQL and SQL Server define their schema as code and apply versioned
migrations at startup under a database lock, or export the script for a deployment that applies
schema changes itself; Redis and MongoDB store the same records in their own shapes.

**Execution.** The worker runs queues concurrently, retries with backoff, enforces rate and time
limits, honors revocations, and settles each outcome through a transactional recorder: with
PostgreSQL or SQL Server behind both the result backend and the inbox, a result and its processed
message commit together, so a crash cannot run the task twice or lose it. Circuit breakers stop
consumption of a failing queue and resume it when it recovers; graceful shutdown returns what it
has not started; dead letters keep what was refused.

**Canvas, schedules, and sagas.** Chains carry their remaining steps on the message, groups
flatten nested members, and chords run a callback when their batch settles. A group followed by a
task is a chord, and a chord is rejected where it is built if it is put inside a group, since it
carries its own callback. Beat elects one scheduler per `SchedulerName` over shared storage and
persists run times across restarts; sagas advance and compensate through completion handlers.

**Generated dispatch.** A Roslyn analyzer reports duplicate task names, and a source generator
registers the tasks an assembly defines through typed references, attaches a typed invoker to
each, records the input and output types with the registration, and emits a signature helper
(`Email(input)`) so canvas code does not spell out type arguments. The reflective scan remains
for assemblies that need it. Core, Worker, Client, and the in-memory providers are
`IsAotCompatible`, and the storage stores serialize through generated contexts, so a Native AOT
application registers its payload types with a `JsonSerializerContext` and runs without
reflection or expression compilation.

**Security and operations.** Messages can be signed with HMAC, checked against a task allowlist,
bounded by payload size and schema version, and refused past a maximum age; the inbox keeps a
processed ID at least as long as that window, so a captured message cannot be replayed inside it.
The dashboard denies requests until its authorization callback is wired, requires the dashboard
header and an allowed origin for state changes, and reports queue statistics, task records,
per-task metrics, and live worker status over SignalR. Health checks, meters, and traces are
registered with one call each.

## Upgrade

DotCelery 1.0.0 is the first stable release. It requires .NET 10 and C# 14, and it freezes the
public surface of all 18 packages in `PublicAPI.Shipped.txt`; an API change that is not declared
in an API file fails the build from here on.

Upgrading from 0.1.0 is a re-registration rather than a drop-in change. Stores now run on the
storage primitives with provider-specific options and migrations, task registration comes from
the generated `RegisterTasks()` where an assembly defines its tasks, and the canvas primitives,
message security, and dashboard providers have their 1.0 shapes. The analyzer package is
optional: without it, tasks register by hand or through the reflective scan and invoke through
the compiled delegate.

All 18 packages are published together at 1.0.0. No package depends on the analyzers.

### Added

- Brokers for RabbitMQ, Redis Streams, Amazon SQS, and in-memory delivery, with one contract
  suite, declared capabilities, and queue metrics recorded as messages are published
- Result backends and stores for Redis, PostgreSQL, SQL Server, MongoDB, and memory, all on the
  storage primitives and the same conformance tests
- Canvas chains, nested groups, and chords, with typed signature helpers generated per task
- Batches with a once-only completion callback, sagas with compensation, and Beat scheduling with
  leader election and persisted state
- Message signing, task and payload allowlists, schema-version and message-age validation, and
  inbox replay defense
- Dashboard data providers, SignalR notifications, and fail-secure authorization
- Source-generated task registration, typed invokers, and input/output metadata
- `IsAotCompatible` core libraries and a published Native AOT smoke test

### Changed

- A message that arrives before its ETA waits without holding the intake loop, and is not counted
  again on every redelivery
- The worker's registry is built from the names recorded with the registrations instead of
  reading each task's `TaskName` through reflection
- A task is invoked through its generated adapter; only a registration without one falls back to
  compiling an expression delegate
- `Group` rejects a chord member when it is built, instead of when the canvas is sent
- The dashboard's worker registry is shared through storage when the application registers one;
  the in-process registry remains the default

### Fixed

- Historical metrics keep snapshots that share a timestamp but differ by queue or task name
- Task records and the task-name list no longer miss names whose records left the newest page
